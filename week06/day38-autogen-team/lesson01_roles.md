> 承接 Day36–37：你会雇 `AssistantAgent`、开 `RoundRobinGroupChat`；今天把「写手–评审」扩成**三人开发小队**。

## 类比：一场短站会

想象一个很小的需求（比如「写一个把摄氏度转成华氏度的函数」）丢进会议室：

| 工位 | Agent 名（本课约定） | 干什么 | 不干什么 |
|------|----------------------|--------|----------|
| **研究员** | `researcher` | 把需求拆成要点、约束、输入输出 | 不写长代码 |
| **程序员** | `coder` | 按研究员要点写出**短**实现（伪代码或几行 Python） | 不自己验收对错 |
| **测试员** | `tester` | 列 2～3 条用例；觉得够了就说 **`APPROVE`** | 不重写整份需求 |

为什么拆三个？  
**一个大脑容易糊成一锅粥**（又调研又写又测，角色互相打架）。拆开后：每人只守一块，对话里能看见「谁说了什么」。

## 和 Day36–37 的对照

| | Day36–37 | 今天 Day38 |
|--|----------|------------|
| 人数 | 写手 + 评审（2） | 研究员 + 程序员 + 测试员（3） |
| 会议室 | `RoundRobinGroupChat` | **同一个** API，名单多一个人 |
| 共享什么 | 群聊里的消息列表 | 还是消息列表 = 小队的「共享状态」 |
| 何时散会 | `APPROVE` 或消息条数上限 | 同样：测试员 `APPROVE`，或 `MaxMessageTermination` |

口诀：**角色变了，会议室骨架没变。**

## 发言顺序（RoundRobin = 按名单轮流）

本课默认名单顺序：

```text
researcher → coder → tester → researcher → coder → …
```

```text
用户任务
   │
   ▼
┌─────────────────────────────────────┐
│  RoundRobinGroupChat                │
│  [researcher, coder, tester]        │
│                                     │
│  共享状态 = 到目前为止的全部消息     │
└─────────────────────────────────────┘
   │
   ▼
有人说出 APPROVE  或  消息条数到上限  → 散会
```

| 协作方式 | 人话 | 本课用不用 |
|----------|------|------------|
| **对话式 / 轮转** | 按固定顺序轮流说话 | ✅ `RoundRobinGroupChat` |
| **选型式** | 模型每次选「下一个该谁」 | 今日不展开（`SelectorGroupChat`） |
| **层级式** | 经理分派下属 | 今日不展开（更偏 CrewAI Process） |

## 「状态共享」一句话

在 AgentChat 的 GroupChat 里，**状态主要就是对话历史**：后发言的人能看到前面所有人的话。  
研究员写的要点 → 程序员看得见 → 测试员也看得见。没有另建数据库也算「多人共享状态」。
