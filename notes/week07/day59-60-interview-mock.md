# Agent 岗系统设计面试：四步骨架、两套案例与追问怎么答

项目做完、简历写好之后，面试常问：「设计一个智能客服 / 投研 Agent」。  
本文给你一套**可复用的口述顺序**，并用电商客服 RAG、自动化投研 Multi-Agent 两套本教程案例示范；再补性能、故障、幻觉三类追问，以及一场 Mock 复盘里最该改的一点。

## 你将会得到什么

1. 澄清 → 架构 → 瓶颈/监控 → 权衡 四步开口顺序  
2. 客服「先库后 FAQ」怎么讲到监控与数字  
3. 投研三人 sequential 怎么讲到韧性与不荐股  
4. P99 / 依赖挂了 / 怎么证明没瞎编 三类追问口径  
5. Mock 后如何改「澄清」里漏掉的一致性问题

## 零基础名词表

> 建议先读完再对着镜子练口述。每个词：**是什么 → 在本文干什么 → 怎么区分**。

### 系统设计面试（LLM / Agent 岗）

| 层 | 说明 |
|----|------|
| **是什么** | 用白板/口述讲清系统怎么拆、数据怎么流、哪会挂、如何取舍 |
| **在本文干什么** | 不考背组件名，考你能否按顺序把客服/投研讲清楚 |
| **怎么区分** | 不是手撕 Transformer；也不是只背「用了 LangChain」 |

### 四步骨架

| 层 | 说明 |
|----|------|
| **是什么** | 澄清 → 架构 → 瓶颈/监控 → 权衡 |
| **在本文干什么** | 每道设计题都按这个顺序开口 |
| **怎么区分** | 一上来堆 Kafka/向量库 = 跳过澄清；只画框不谈监控 = 缺第三步 |

### 检索/路由型 vs 多智能体流水线

| 层 | 说明 |
|----|------|
| **是什么** | 两种常见 Agent 业务形态 |
| **在本文干什么** | 客服 = 先精确查库再 FAQ；投研 = 搜集→分析→成稿交接 |
| **怎么区分** | 都「用了大模型」不够；要说清主路径差异 |

### 大盘 vs 单次（面 / 点）

| 层 | 说明 |
|----|------|
| **是什么** | 监控看一段时间整体；日志/`request_id` 看这一枪 |
| **在本文干什么** | P99 升高时：先 Grafana，再日志，再分 Postgres vs FAQ |
| **怎么区分** | 别一上来改向量化；先证明慢在哪一段 |

### 重试与降级

| 层 | 说明 |
|----|------|
| **是什么** | 偶发失败再试；试尽仍给可读结果（如 fixture） |
| **在本文干什么** | 投研搜索超时：重试 + 降级，避免整条 Crew 断死 |
| **怎么区分** | 只重试无兜底 → 仍会挂；降级要标明非实时 |

```text
面试题
  → 四步骨架
  → 套客服或投研案例
  → 准备追问（性能 / 故障 / 幻觉）
  → Mock → 改澄清遗漏点
```

## 规矩一：四步怎么开口

| 步 | 你要干什么 | 例子问题 |
|----|------------|----------|
| 1 澄清 | 钉范围、规模、失败策略、一致性 | QPS/P99？未命中转人工？订单能否缓存？ |
| 2 架构 | 主路径组件与数据流 | 入口 → 核心 → 存储/模型 |
| 3 瓶颈/监控 | 哪会慢/挂；怎么看见 | 指标、告警、日志 ID |
| 4 权衡 | 至少一个选 A 不选 B | 准 vs 快；可审计 vs 并行 |

口诀：**先问清楚再画图；画完说哪疼、怎么盯；最后说取舍。**

---

## 规矩二：客服案例（检索/路由型）

**澄清：** 订单/SKU 事务 vs 政策 FAQ；目标可参考 QPS>200、P99<500ms；未命中允许 `need_human`；**订单是否必须实时查库（vs 分钟级缓存）**。

**架构：** `POST /ask` → 有标识则 **先 Postgres** → 否则/未命中再 **FAQ** → 仍不够则转人工；Compose 整栈部署。

**瓶颈/监控：** 库热点与 FAQ 检索；本机 Locust 库路径约 QPS≈281、P99≈250ms；Prometheus `/metrics` + Grafana；`request_id` 对单次。

**权衡：** 先精确库再模糊文档，不让模型编订单状态；FAQ 生产可升级向量检索，**路由优先级不变**。

---

## 规矩三：投研案例（多智能体流水线）

**澄清：** 输入公司名；**不荐股**；工具失败能否降级；中间稿要否可审计。

**架构：** 搜集 → 财报分析 → 撰写；`Process.sequential` + `context`；≥5 工具按职责挂载。

**瓶颈/监控：** 模型慢/胡说；工具抖动 → 重试 + fixture 降级；`intermediate/` 分步对账。

**权衡：** sequential 可审计，不选三人一起抢（交接乱）。

---

## 规矩四：三类追问

### 性能（P99 升高）

1. Grafana：是否全站、何时起、QPS 是否突增  
2. `request_id` + `duration_ms`：单次卡在哪  
3. 分路径：Postgres vs FAQ；必要时 Locust 对比  

口诀：**大盘看面，日志看点。** 证据不足时不要先改向量化。

### 故障（搜索一直超时）

只重试无兜底 → 搜集步空 → 整条断。  
应：**重试扛偶发 + fixture/缓存降级**，标明非实时，后续 `context` 仍可继续。

### 评估 / 幻觉

- 客服：看 `source`（db / faq / need_human）  
- 投研：看中间稿交接；不荐股、不编未查数字  
- 有来源标签或交接物可对账，才算没瞎编  

**空话改实例子**

- 空：「我们会加强监控保证稳定。」  
- 实：点出 `/metrics`、Grafana、`request_id`、Locust 基线，或投研的重试/降级与 `intermediate/`。

## Mock 复盘：最该补的一句

一场客服 Mock 里，主答与「面→点→分路径」追问可以很稳，但澄清常漏：

> 订单状态是否允许分钟级缓存？必须强一致则直查 Postgres；可缓存再谈命中率与失效。

把这句写进澄清提纲，下次开口主动问，少被「能不能缓存」追到。

## 小结

Agent 岗系统设计不是堆名词，而是 **顺序固定、案例落地、追问能指到证据**。  
客服用路由与监控说话，投研用协作与韧性说话；Mock 后把澄清里漏掉的一致性问题补进提纲，比再背十个框架名有用。
