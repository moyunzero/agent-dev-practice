# 把两个 Agent 项目写进开发岗简历：结构、量化与数字纪律

做完智能客服和投研 Agent 之后，还差关键一步：**按开发岗模板，把经历量化写进简历**。  
本文不讲排版美化，只讲三条硬规矩：项目条三段结构、两条项目怎么写亮点、哪些数字能写死 / 只能占位。

参考：[Tech Interview Handbook · Resume](https://www.techinterviewhandbook.org/resume/) · 上游路线「开发岗简历必备」与两项目「简历亮点」。

## 你将会得到什么

1. 一条经历 = 背景 + 动作 + 量化结果  
2. 客服条：先库后 FAQ + QPS/P99 + 监控/Compose  
3. 投研条：三人流水线 + ≥5 工具 + 重试/降级  
4. 数字纪律：测过的写死，没测的用 XX 或不写  
5. 一份可粘贴的双项目 Markdown 块  

---

## 零基础名词表

> 建议先读完再改自己的简历。每个词：**是什么 → 在本文干什么 → 怎么区分**。

### 开发岗简历项目条

| 层 | 说明 |
|----|------|
| **是什么** | 简历上「项目经历」里的一段：标题 + 若干 bullet |
| **在本文干什么** | 把客服、投研各写成可粘贴块 |
| **怎么区分** | 不是博客长文，也不是「负责参与」空话；招聘方 3 秒要看到你做了什么、结果如何 |

### 背景 / 动作 / 量化结果

| 层 | 说明 |
|----|------|
| **是什么** | 写 bullet 的三段骨架 |
| **在本文干什么** | 每条经历至少能拆出这三段 |
| **怎么区分** | 「效果很好」不是结果；「本机 Locust QPS≈281」才是可追问的结果 |

### 量化指标（QPS / P99）

| 层 | 说明 |
|----|------|
| **是什么** | QPS≈每秒请求数；P99≈最慢那 1% 请求的延迟上界感 |
| **在本文干什么** | 客服项目用本机压测数字支撑「高并发 / 低延迟」 |
| **怎么区分** | 要写清「本机 / 某路径」；不要假装公有云线上 SLA |

### 数字纪律与 XX 占位

| 层 | 说明 |
|----|------|
| **是什么** | 只写面试官能追问「怎么测的」的数字 |
| **在本文干什么** | 「节省人力 / 提升效率」无对照实验 → 用 XX% 或删除 |
| **怎么区分** | 占位是诚实草稿；写死未测的 80%、50% 是简历事故 |

### 检索/路由型 vs 多智能体流水线

| 层 | 说明 |
|----|------|
| **是什么** | 两个项目的「类型标签」，方便并排扫读 |
| **在本文干什么** | 客服 = 先库后文档；投研 = 多人顺序交接出报告 |
| **怎么区分** | 都用了 LLM 不够；要写出系统形态差异 |

```text
上游亮点句
  → 客服：高并发/低延迟/监控/部署  ← 落到 Locust + Compose + Prom
  → 投研：Multi-Agent/工作流/人效XX ← 落到三人+工具+韧性；人效用占位
  → 粘贴进简历
```

- 无需新装依赖；准备你已跑通的两个项目证据（或等价笔记）  
- 建议对照：客服压测与 Compose 笔记；投研 Crew 与工具笔记

## 规矩一：三段结构

**差例：**「负责智能客服，用了 AI，效果很好。」

**改好方向：**

> 为电商客服场景搭建问答 API（背景）；实现先 Postgres 再 FAQ 的路由，并用 Locust 压测（动作）；本机 QPS≈281、P99≈250ms（结果）。

口诀：**谁的问题 → 我做了啥 → 结果用数字说。**

---

## 规矩二：客服条写什么

对齐上游亮点，落到可辩护证据：

| 亮点 | 可写 |
|------|------|
| 高并发 / 低延迟 | 本机 Locust（库路径）QPS≈281，P99≈250ms（门槛 <500ms） |
| 生产级监控 | Prometheus `/metrics` + Grafana；请求 `request_id` |
| 部署 | Docker Compose 整栈（API + Postgres + Prom + Grafana） |
| 节省 XX 人力 | **未测** → 占位或不写 |

业务一句：**`POST /ask` 先精确查库，未命中再 FAQ。**

示例 bullets：

```markdown
- 实现电商客服 POST /ask：先 Postgres 精确查订单/SKU，未命中再 FAQ 回退；
  本机 Locust（库路径）QPS≈281，P99≈250ms（门槛 <500ms）。
- 以 Docker Compose 部署 API + Postgres + Prometheus + Grafana 整栈；
  Instrumentator 露出 /metrics，请求日志带 request_id；Grafana 看 QPS/P99。
```

## 规矩三：投研条写什么

| 亮点 | 可写 |
|------|------|
| Multi-Agent | 搜集 / 财报分析 / 撰写 |
| 工作流自动化 | `Process.sequential` + `context`；中间产出落盘可审计 |
| ≥5 工具 | 搜索、概览、SEC、指标、写文件等 |
| 稳定性 | tenacity 重试 + fixture 降级 |
| 提升 XX% 效率 | **未测人效** → 占位或不写 |

示例 bullets：

```markdown
- 用 CrewAI 搭建搜集 / 财报分析 / 撰写三人小队，sequential + context 接力；
  每步中间产出落盘，可审计分析是否完成。
- 集成 ≥5 工具；工具层重试 + fixture 降级，抖动下仍能交出可用文本。
```

一句话差异（并排扫读用）：

- **客服** = 检索/路由型（先库后 FAQ，重性能与监控部署）  
- **投研** = 多智能体流水线（搜集→分析→成稿，重协作、工具与韧性）

## 规矩四：数字纪律（动手改一句）

把虚数改成可辩护表述：

**虚数：**「投研 Agent 上线后效率 +50%，成功率 99.9%。」

**可辩护方向：** 写清三人流水线、工具与重试/降级；成功率若未做统计就写「占位 XX%」或只写「本仓脚本可验证仍能出可用文本」——**不要写死未测的 50% / 99.9%。**

自检：每条数字，你能否指出「哪条命令 / 哪次跑」测出来的？

## 可粘贴样例（双项目）

下面是按上述规矩整理的样例块（数字为本教程示例口径；粘贴前按你自己的实测核对）。

```markdown
## 企业级智能客服 RAG（电商）
为电商场景搭建「先查库、再 FAQ」的智能客服 API，并完成监控与 Compose 整栈部署。
- 实现 POST /ask：先 Postgres 精确查订单/SKU，未命中再 FAQ；本机 Locust（库路径）
  QPS≈281，P99≈250ms（门槛 <500ms）。
- Compose 部署 API + Postgres + Prometheus + Grafana；/metrics + request_id；Grafana 看 QPS/P99。
技术栈：FastAPI · PostgreSQL · FAQ · Prometheus · Grafana · Docker Compose · Locust

## 自动化投研 Agent
为投研分析师搭建「公司名 → 搜集→分析→成稿」的 CrewAI 多智能体流水线，中间产出可审计、工具层可降级。
- 三人小队 + sequential/context；中间产出落盘可审计。
- ≥5 工具；tenacity 重试 + fixture 降级，抖动下仍能交出可用文本。
技术栈：CrewAI · Ollama · Custom Tools（≥5）· tenacity · fixture（Search/SEC 等价）
```

## 边界：做了什么 / 故意没做什么

| 做了 | 没做 |
|------|------|
| 两项目可粘贴 Markdown | 精美 PDF / 一页纸排版课 |
| 对齐上游亮点与开发岗必备 | 编造线上 DAU、营收、未测人力 |
| 数字纪律与 XX 占位 | Day59–60 系统设计题与 Mock 面试（下一块） |

---

## 小结

简历上的项目经历不是「技术名词堆砌」，而是 **形态说清 + 动作说清 + 数字可辩护**。  
客服用压测和监控说话，投研用协作和韧性说话；测不到的人效，诚实占位或删掉，比写死虚数安全。
